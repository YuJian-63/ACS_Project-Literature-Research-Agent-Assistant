## 3. 最近调整与保留的限制

- 新单篇任务使用内部 `evidence-v4`，新综述使用 `evidence-review-v2`：模型选择服务端提供的 evidence_id，由服务端取得逐字原文及来源身份并统一编号。正文与表格共享引用池，保持错源/未知证据/非法 JSON 拒绝和原子发布。
- 新建真实综述冻结 4096 Token 输出上限，请求上限仍受剩余预估总预算限制，调用后的实际用量仍检查总预算。旧任务/原幂等键重放及单篇任务保持 2048；Mock 不变。不自动续写、修补 JSON 或付费重试。
- 4096 是上限而非成功保证；成功任务实际用量未经独立核查，不能推断它必然用了超过 2048，也不能把一次成功视为对调整效果的受控实验。
- 引文来自正确原文只建立可追溯性，不自动证明它支持对应结论；需单独做语义评测。
- 部署仍限定本机单用户。无 OCR、无向量索引、无全自动搜读循环；失败模型调用的 usage 也并非全部持久化，失败不等于费用为零。

## 4. 优先级与交付顺序

采用“可复现基线 → 可量化评测 → 检索/Agent 扩展 → 模型部署对接”的顺序。它便于后续将改进与同一模型、输入、来源及预算下的基线比较。检索和 Agent 的具体方案应分别形成独立设计，不在本轮同时展开。

| 优先级 | 工作包 | 主要交付 | 验收门槛 |
| --- | --- | --- | --- |
| P0 | 正式测试与 CI，补齐 MVP-2.1 工程部分 | 仓库内 tests、脱离 runtime 的 fixture、统一命令、隔离 PostgreSQL 集成检查、前端构建/浏览器关键路径 CI | 干净克隆可复现；默认不连接真实来源/模型，不需要个人密钥 |
| P1 | 可重复质量评测 | 小型标注集、评分规则、批次结果与失败分类 | 摘要/QA/综述均覆盖；明确支持率、准确率、覆盖率、完成率和用量统计口径 |
| P1 | 运行与演示可复现 | 启动指南、脱敏配置、就绪检查、失败排查及演示步骤 | 新终端可按文档启动；离线演示不依赖 arXiv；配置检查不泄露密钥 |

## 5. 下一轮具体任务：P0 正式测试与 CI

以下为分步建议，尚未执行。先后关系是 1 → 2 → 3 → 4；每步以实际通过的检查与清晰提交范围收尾。

### 任务 1：落地后端离线测试入口

- 建议路径：`backend/tests/unit/`、`backend/tests/fixtures/`、`backend/tests/README.md`；如采用标准 unittest 可暂不新增测试框架依赖。
- 从现有 runtime 脚本迁移引用协议、结果诊断、任务配置冻结与输出预算等确定性检查；去掉对被忽略脚本的动态导入和本机绝对路径依赖，夹具只保留最小合成文本/模型响应。
- 先建最小有效测试入口，再分组搬迁；不因已存在 190 项检查而机械承诺迁移后的测试数量必须相同。重点保留相同风险覆盖和拒绝路径。
- 目标命令：在 backend 执行 `uv run --locked python -m unittest discover -s tests/unit -v`。
- 验收：不读取个人 .env；不依赖 runtime、运行数据库、真实 PDF 全文、来源网络或模型密钥；覆盖历史缺字段 2048、新 review 4096、非法 cap 拒绝、余量/耗尽预算、截断不发布与不自动重试。

### 任务 2：落地原生数据库隔离集成测试

- 建议路径：`backend/tests/integration/` 和独立夹具；参考现有原生验收守卫，但不要复制验收库凭据到测试。
- 接受明确的测试数据库配置，启动时校验测试目标，使用临时独立库/命名空间和临时存储，拒绝使用用户业务数据库；清理仅限本轮夹具。
- 覆盖真实迁移、幂等并发、行锁/领取、租约过期/旧持有者拒写和产物事务回滚；模型和来源响应使用夹具。
- 验收：PostgreSQL 17 上可重复运行，失败退出非零，cleanup 不破坏业务数据，不把兼容层单连接检查替代真实并发结果。

### 任务 3：前端关键路径进入版本管理

- 建议路径：`frontend/tests/e2e/`；测试入口和依赖管理需在实现时选择一种并冻结，避免同时维护两套浏览器测试框架。
- 迁移搜索结果保留/精确页重试/429 冷却、任务幂等提交、刷新恢复和引用/表格展示的核心场景，桌面与移动端分别检查。
- 所有 HTTP 响应采用路由夹具或隔离测试服务，不启动用户已有 API/Worker，不发真实 arXiv 或付费模型请求。
- 验收：保留 `npm.cmd run build`，提供一条可从干净克隆安装依赖并执行浏览器检查的明确命令；对页面错误和未拦截 API 请求显式失败。

### 任务 4：配置自动检查并收尾

- 建议路径：`.github/workflows/ci.yml`、相关 README；固定到项目声明兼容的 Python/Node 和 PostgreSQL 主版本，使用锁文件安装。
- 拆分离线后端、原生数据库集成、前端类型/构建及浏览器检查；日志不得包含个人环境或凭据，报告/截图保留为短期 CI 产物。
- 依赖、浏览器二进制安装可能需要下载权限；实际启用远端 CI 需要后续明确推送授权。离线场景通过不等于已观察到远端 CI 绿色结果。
- 验收：工作流配置、本地等价命令和隔离数据库检查通过；推送后再单独记录真实 CI 运行结果。提交只含源码、最小夹具、锁文件和文档。

## 6. 后续评测建议

建议先准备约 8—12 个小型人工标注场景，再逐步扩充；该数量是建议规模，不是已经存在的数据或达标率。场景应覆盖单篇摘要、可回答 QA、不可回答 QA、双篇共同点/差异、冲突发现、条件不可比，以及检索不到有效证据。

每项至少记录：固定论文/问题、预期事实与原文页码、禁止推断、使用的模型/工作流/提示版本及预算。对齐提案中的 Key-Fact Coverage、Answer Accuracy、Comparison Accuracy、Citation Support Rate，并记录任务完成率、耗时、Token 和模型/工具调用。未知实际用量保留未知，不按零计算；成本按可核查的当时计费信息计算，不在本路线图估算金额。

生成质量测试与确定性 CI 分离。付费评测批次须先明确样本数、模型和预算，不在普通提交检查中自动运行。摘要当前 v4 的独立真实验收、更多篇综述及特殊 PDF 的覆盖，应作为补充样本而非为追求任务数反复付费重试。
